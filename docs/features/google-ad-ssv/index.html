🔑
한 줄 요약. 클라이언트가 "광고를 봤다"는 주장을 믿지 않는다. AdMob 서버가 우리 백엔드로 직접 보내는 Google 서명된 콜백만 신뢰한다. 그리고 "누구에게 적립할지"는 클라가 채운 user_id를 직접 믿는 대신, 서버가 발급한 단일 사용 nonce로만 해석한다.

2. 동작 흐름 (시퀀스)

sequenceDiagram
    actor User as 사용자
    participant FE as 앱 클라이언트
    participant SDK as AdMob SDK
    participant AdMob as AdMob 서버
    participant API as CashChat 백엔드
    participant DB as DB

    Note over User,DB: 1단계 — nonce 발급 (동기, 시청 직전)
    User->>FE: 혜택존 지금 시청
    FE->>API: GET /api/ads/reward/quota
    API-->>FE: usedToday, remaining
    FE->>API: POST /api/ads/reward/issue-nonce (JWT)
    API->>DB: ad_reward_nonce INSERT (used=false)
    API-->>FE: nonce, expiresAt
    FE->>SDK: setUserId(nonce) 후 광고 노출
    User->>SDK: 광고 끝까지 시청

    Note over User,DB: 2단계 — SSV 콜백 검증·저장 (무트랜잭션)
    AdMob->>API: GET /api/ads/google/ssv?...signature...key_id
    API->>API: 파싱 → ad_unit 검증 → 공개키 조회 → ECDSA 서명 검증
    alt 서명/파싱 실패
        API-->>AdMob: 400 (미저장)
    else 공개키 조회 불가
        API-->>AdMob: 503
    else 검증 성공
        API->>DB: google_ad_ssv_events UPSERT (VERIFIED)
        Note over API,DB: 3단계 — 적립 (단일 TX · 락: event→nonce→quota→point)
        API->>DB: ad_reward_nonce 락 조회 (user_id=nonce)
        alt nonce 없음/만료/used
            API->>DB: status=REJECTED_INVALID_NONCE
            API-->>AdMob: 200
        else nonce 유효
            API->>DB: daily_quota 락 조회/생성
            alt 한도 초과
                API->>DB: nonce.used=true; status=REJECTED_OVER_QUOTA
                API-->>AdMob: 200
            else 한도 내
                API->>DB: quota+1; nonce.used=true
                API->>API: recordTransaction(코인, key=admob:reward:txId)
                API->>DB: status=GRANTED
                API-->>AdMob: 200
            end
        end
    end

    Note over User,DB: 4단계 — 앱 반영 (별도 조회)
    User->>FE: 광고 종료/복귀
    FE->>API: GET quota · 잔액 조회
    API-->>FE: 갱신된 값

핵심 단계

  1. nonce 발급 — 시청 직전 POST /api/ads/reward/issue-nonce → { nonce, expiresAt }. nonce↔userId 매핑을 서버가 보관.
  2. 광고 노출 — nonce를 SSV user_id에 실어 보상형 광고 present.
  3. SSV 콜백 — AdMob 서버가 GET /api/ads/google/ssv로 서명된 콜백 전송.
  4. 검증·저장 — 서명(SHA256withECDSA) 검증 후 이벤트 저장(VERIFIED). 적립 안 함.
  5. 적립 — nonce→userId 해석 → 일일 한도 확인 → 코인 적립 → GRANTED.
  6. 앱 반영 — 비동기라 즉시 안 뜸 → 잔액/quota 재조회.

3. 이벤트 상태 전이

stateDiagram-v2
    [*] --> VERIFIED: 서명 검증·저장
    VERIFIED --> GRANTED: nonce 유효 · 한도 내 · 코인 적립
    VERIFIED --> REJECTED_INVALID_NONCE: nonce 없음/만료/이미 사용
    VERIFIED --> REJECTED_OVER_QUOTA: 일일 한도 초과
    GRANTED --> [*]
    REJECTED_INVALID_NONCE --> [*]
    REJECTED_OVER_QUOTA --> [*]

VERIFIED

서명 검증·저장 완료, 적립 미결정 상태. 적립 실패로 남으면 AdMob 재전송 시 재시도된다.

GRANTED

코인 적립 완료(종결). 재전송돼도 멱등하게 건너뜀.

REJECTED_INVALID_NONCE

nonce가 없거나 만료/이미 사용됨. 위조·재사용 차단. 200 반환(적립 X).

REJECTED_OVER_QUOTA

오늘 시청 한도 초과. 유효 nonce는 소모 처리. 200 반환(적립 X).

4. 보안·정합성 설계

🔏 서명 검증 우선

key_id의 Google 공개키로 SHA256withECDSA 검증. 페이로드는 signature 앞 원본 쿼리스트링 → 파서가 signature·key_id를 마지막 두 파라미터로 강제.

🎫 nonce 신뢰 모델

SSV user_id는 클라가 임의로 채우는 값 → 직접 신뢰 X. 서버 발급 단일 사용 nonce로만 nonce→userId 해석. 타인 계정 적립 위조 차단.

♻️ 멱등 이중 방어

transaction_id UNIQUE dedup + 적립 멱등키 admob:reward:{transactionId}. 재전송에도 1회만 적립.

🔒 락 순서 고정

데드락 방지: event → nonce → daily_quota → user_point 비관적 쓰기 락. 동시 콜백의 상태 덮어쓰기·중복 적립(TOCTOU) 차단.

🔁 재시도 폭주 방지

서명만 통과하면 거절 케이스도 200 반환. 적립 실패도 5xx 안 던짐 → AdMob 무한 재전송 방지. (서명 실패만 400, 공개키 불가 503.)

🎯 광고단위 검증(선택)

rewarded-ad-unit-ids(콤마 구분, Android·iOS) 설정 시 콜백 ad_unit 목록 일치 강제. 빈 값이면 스킵.

6. ⚠️ 현재 핵심 갭 & 설계 이력

⚠️
프론트–백엔드 위치 불일치. 백엔드는 nonce를 SSV user_id에서 읽지만, 현재 앱 클라이언트는 nonce를 custom_data(setCustomData/customRewardText)로 싣는다. 이를 setUserId/userIdentifier로 바꾸기 전까지 실제 적립은 end-to-end로 동작하지 않는다. → manual.md §2

적립 경로 정리 (왜 이렇게 됐나)

초기엔 두 적립 경로가 같은 콜백에 얽혀 있었다 — ① 코인 경로(nonce 기반, 40코인 고정)와 ② ledger 경로(후행 추가, reward_amount 기반 회계 분배). ledger 경로가 user_id를 숫자로 강제(toLongOrNull)하면서 nonce·이메일 입력에 400을 유발했다.

결정: 정본 = 코인 경로(nonce). GoogleAdSsvService에서 숫자 강제·ledger 적립 제거(검증+저장만). 리워드 광고는 코인만 적립(energy·매출회계 없음). LedgerService는 휴면 상태로 보존.
