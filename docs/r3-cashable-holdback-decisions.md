# R3 — cashablePt 보류→확정(holdback) 설계 결정사항

> **목적** — 개정 경제 모델(CC-283)의 **R3 슬라이스**를 구현하기 전에 *반드시 확정해야 하는 결정사항*을
> 모아 둔 체크리스트다. 아직 구현된 코드가 아니며, 각 항목은 **정본 스펙(Confluence CC-283)** 기준으로
> 확정한 뒤 착수한다.
>
> **상태** — 미착수(결정 대기). R1·R2·광고 밥 보상은 완료([PR #214](https://github.com/cash-chat-mvp/cash-chat-mvp/pull/214)).

## 배경 — R3가 푸는 문제

현재(R1) 채팅 정상 완료 시 `ChatRewardService.settle` 이 `cashablePt +1`(`CHAT_REWARD`)을
**즉시 인출 가능한 잔액으로 직접 적립**한다. 즉시·불가역 적립은 다음 리스크에 노출된다:

- **파밍**: 의미 없는 채팅을 대량 반복해 cashablePt 를 긁어 즉시 현금화.
- **불가역**: 부정 사용자로 판명돼도 이미 인출되면 회수 불가.
- **품질 미검증 보상**: "유효 완료" 기준이 느슨할 때 잘못 적립된 보상을 취소할 장치가 없음.

R3는 보상을 **보류(pending) → 확정(confirm)** 2단계로 나누고, 확정 전 **취소(revoke)** 가 가능하게 한다.

---

## 정해야 하는 항목 (Decision Points)

### D1. 보류 잔액을 어떻게 표현할 것인가
- (a) `user_point` 에 `pending_balance` 컬럼 추가 (confirmed 와 분리된 두 잔액)
- (b) 별도 `pending_reward` 테이블 (행별 만기·상태 추적)
- (c) `point_transaction` 에 상태 플래그(PENDING/CONFIRMED/REVOKED) 추가
- **결정 필요**: 위 중 무엇? 출금/거래내역 요구사항과 정합성 고려.

### D2. 확정(confirm) 트리거
- (a) **시간 지연**: 적립 후 D+N (예: D+1~D+7) 경과 시 자동 확정
- (b) **누적 임계치**: 일정량 이상/특정 행동 후 확정
- (c) **검증 통과**: 어뷰징·품질 체크 통과 시 확정
- (d) **출금 시점 lazy 확정**: 출금 요청 시 보류 윈도 지난 분만 확정
- **결정 필요**: 단일/조합? N값(보류 윈도)은? — 정본 스펙 수치 확인.

### D3. 확정 실행 주체
- (a) **스케줄러 배치**(예: 매일 KST 정시 만기 도래분 일괄 확정)
- (b) **이벤트 기반**(특정 행동 발생 시)
- (c) **lazy**(조회/출금 시 계산)
- **결정 필요**: 배치라면 주기·타임존(전 채널 KST 통일 권장)·멱등 키 설계.

### D4. 취소(revoke) / 몰수 조건
- 어뷰징 판정 시 **보류분(pending)만** 소멸시킬지, 이미 확정분도 회수할지.
- 판정 기준(예: 단시간 대량 적립, 동일 기기 다계정)과 근거 정책.
- **결정 필요**: revoke 트리거·권한(자동 vs 운영자 수동)·감사 로그.

### D5. 원장·멱등성
- pending 적립, pending→confirmed 이관, revoke 각각을 **원장에 기록**할지 / 멱등 키 형식.
- 기존 `CHAT_REWARD` 사유를 유지할지, `CHAT_REWARD_PENDING`/`CHAT_REWARD_CONFIRMED` 등으로 분리할지.
- **결정 필요**: `PointTransactionReason` enum 확장 여부.

### D6. R1 연결 지점 변경
- `ChatRewardService.settle` 의 `cashablePt +1` **직접 적립 → 보류(pending) 적립**으로 변경.
- 변경 범위: `UserPointService` 에 보류 적립 API 신설 또는 별도 서비스.
- **결정 필요**: R1 코드와의 인터페이스(메서드 시그니처) 설계.

### D7. 노출(API)
- 사용자/내부에 **pending vs confirmed 분리 노출** 여부 (예: 마이페이지 "확정 예정 N").
- **결정 필요**: 응답 DTO·필드명.

### D8. 마이그레이션 / 기존 적립분 처리
- 새 컬럼/테이블 Flyway 버전(V14+).
- R1에서 **이미 즉시 적립된 cashablePt** 를 소급 보류로 돌릴지(보통 그대로 둠).
- **결정 필요**: 마이그레이션 스크립트 범위.

### D9. 출금(cashout)과의 관계
- 현재 출금 기능은 **미구현**(`docs/service-operation.md` §4.4). 보류→확정은 출금의 전제이므로
  출금 도입 시 보류 윈도·세무·본인인증과 함께 설계해야 함.
- **결정 필요**: R3를 출금과 묶을지, 보류 인프라만 선제 구축할지.
